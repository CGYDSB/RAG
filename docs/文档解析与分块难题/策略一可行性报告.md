# 标题层级感知切片（策略一）在当前项目中的可行性报告

**参考方案**：文档解析与分块难题方案.md — 策略一
**评估对象**：当前 RAG 项目（src/data_loader.py、src/document_splitter.py、src/rag_pipeline.py）
**结论**：可行，主要依赖已具备，改造量可控

---

## 一、策略一的核心目标

让每个 chunk 携带完整的标题归属路径，而不是孤立的正文片段。

**现状（当前项目）**：
```
额定压力：350bar，流量：120L/min
```

**目标（策略一）**：
```
第3章 液压系统 > 3.1 主泵规格
额定压力：350bar，流量：120L/min
```

这解决的核心问题是：检索命中了一段内容，但不知道它属于哪个章节，导致 LLM 无法准确引用来源，也无法理解该内容的语义归属。

---

## 二、当前项目现状分析

### 2.1 data_loader.py — PDF 加载

当前实现只插入了页码标记，未提取文档结构：

```python
# 当前代码（data_loader.py L68）
pages.append(f"[PAGE:{i+1}] {text}")
```

`pypdf` 的 `PdfReader` 已经是项目依赖，它提供 `reader.outline` 属性可直接读取 PDF 书签树，但当前代码完全没有使用。

### 2.2 document_splitter.py — 切分器

当前使用 `RecursiveCharacterSplitter`，纯字符级递归切分，分隔符优先级为：

```python
self.separators = ["\n\n", "\n", ". ", " ", ""]
```

不感知任何标题结构，同一节的内容可能被切断，不同节的内容可能被合并。切出的 `TextChunk` 只有 `content` 和基础 `metadata`（页码、chunk 索引），没有标题路径字段。

### 2.3 rag_pipeline.py — 上下文构建

```python
# _build_context_with_budget()
formatted = f"{citation} {text}"
```

输出给 LLM 的上下文只有引用编号和正文，没有章节归属信息。

## 三、可行性论证

### 3.1 有利条件

**条件一：核心依赖已具备，无需新增**

`pypdf` 已在 `requirements.txt` 中，`PdfReader.outline` 可直接读取书签树，不需要安装额外库。

**条件二：TextChunk.metadata 是开放 dict，可直接扩展**

```python
# document_splitter.py
@dataclass
class TextChunk:
    content: str
    metadata: Dict      # 直接加 section_path 字段即可
    chunk_id: str
    ...
```

不需要改数据结构，只需在 `split()` 时往 metadata 里写入 `section_path`。

**条件三：页码追踪机制已实现，可复用**

`document_splitter.split()` 已经通过 `[PAGE:N]` 标记追踪每个 chunk 的页码。标题路径的注入可以用同样的机制：在 PDF 加载时按页码范围建立"页码 → 标题路径"的映射表，切分时查表写入。

**条件四：知识库文档结构适合**

当前知识库中的 Python 技术手册（`python-doc-27-34.pdf`、`Python学习手册(第4版).pdf` 等）均为正式出版物，普遍带有完整的 PDF 书签目录，Outline 提取覆盖率高，是策略一最适合的文档类型。

### 3.2 制约条件

**制约一：Outline 到文本块的映射需要自行实现**

`pypdf` 的 Outline 只提供书签条目和对应页码，不直接对应文本块。需要实现"文本块属于哪个书签范围"的映射逻辑——按页码区间判断：chunk 的页码落在哪两个相邻书签之间，就归属于前一个书签节点。

RAGFlow 用 bigram 相似度匹配文本内容，精度更高但实现复杂。按页码区间判断是更简单的替代方案，对于有完整书签的 PDF 精度足够。

**制约二：切分器需改造以支持跨 chunk 继承标题路径**

`RecursiveCharacterSplitter` 按字符数切，一个标题节的内容可能被切成多个 chunk。需要在切分时维护"当前所在标题节"的状态，让同一节切出的多个 chunk 都继承相同的 `section_path`。

**制约三：无 Outline 的 PDF 需要正则兜底**

部分 PDF（如扫描版或非正式文档）没有书签目录。RAGFlow 用 `title_frequency()` 通过统计编号模式自动识别标题，当前项目没有对应实现。对于当前知识库影响有限，但作为通用方案需要考虑。

## 四、改造方案

### 4.1 第一步：提取 PDF Outline，建立页码映射表

在 `data_loader._load_pdf()` 中新增 Outline 提取逻辑：

```python
def _extract_outline(self, reader) -> List[Dict]:
    """
    提取 PDF 书签树，返回按页码排序的标题列表
    每项：{'title': str, 'page': int, 'level': int}
    """
    outlines = []

    def _walk(items, level=1):
        for item in items:
            if isinstance(item, list):
                _walk(item, level + 1)
            else:
                try:
                    page_num = reader.get_destination_page_number(item)
                    outlines.append({
                        'title': item.title.strip(),
                        'page': page_num,
                        'level': level
                    })
                except Exception:
                    pass

    try:
        _walk(reader.outline)
    except Exception:
        pass

    return sorted(outlines, key=lambda x: x['page'])


def _build_page_to_section(self, outlines: List[Dict], total_pages: int) -> Dict[int, str]:
    """
    按页码区间建立 page → section_path 映射
    例如：第1-5页属于"第1章 简介"，第6-12页属于"第2章 安装"
    """
    if not outlines:
        return {}

    mapping = {}
    # 维护祖先标题栈，构建完整路径
    for i, outline in enumerate(outlines):
        end_page = outlines[i + 1]['page'] if i + 1 < len(outlines) else total_pages
        # 简化：取当前标题作为 section_path（可扩展为完整祖先路径）
        for page in range(outline['page'], end_page):
            mapping[page] = outline['title']

    return mapping
```

### 4.2 第二步：切分时注入 section_path

在 `document_splitter.RecursiveCharacterSplitter.split()` 中，利用 chunk 的页码查找标题路径：

```python
# 从 document metadata 中取出页码映射表（由 data_loader 写入）
page_to_section = document.metadata.get('page_to_section', {})

# 在构建 TextChunk 时写入 section_path
section_path = page_to_section.get(current_page, '')
metadata = {
    **document.metadata,
    'chunk_index': i,
    'page': current_page,
    'section_path': section_path,   # 新增
}
```

### 4.3 第三步：上下文构建时前置标题路径

在 `rag_pipeline._build_context_with_budget()` 中，输出 chunk 时把标题路径拼入：

```python
section = chunk.metadata.get('section_path', '')
display_text = f"[{section}]\n{text}" if section else text
formatted = f"{citation} {display_text}"
```

LLM 看到的上下文变为：

```
[[1]] [第3章 安装与配置]
安装前请确认系统版本不低于 3.8...

[[2]] [第3章 安装与配置]
使用 pip install 命令安装依赖...
```

## 五、改造工作量评估

| 改造点 | 涉及文件 | 预估代码量 | 难度 |
|--------|----------|-----------|------|
| PDF Outline 提取 + 页码映射 | data_loader.py | ~60 行 | 低 |
| 切分时注入 section_path | document_splitter.py | ~15 行 | 低 |
| 上下文构建时前置标题路径 | rag_pipeline.py | ~5 行 | 低 |
| 无 Outline 文档的正则兜底 | document_splitter.py | ~50 行 | 中 |

核心改造（前三项）合计约 80 行，不涉及架构变动，风险低。正则兜底可作为后续迭代，当前知识库文档有书签的情况下可以先跳过。

## 六、预期收益

**检索质量提升**：chunk 携带章节信息后，向量化时语义更完整，相同正文内容在不同章节下的向量表示会有差异，减少跨章节的误召回。

**引用溯源更精准**：当前引用只能到页码，改造后可以精确到章节，用户看到 `[[1]] 第3章 安装与配置 - 第10页` 比只有页码更有价值。

**LLM 理解更准确**：上下文中带有章节路径，LLM 在生成答案时能更准确地理解内容的语义归属，减少跨章节混淆。

---

## 七、结论

策略一在当前项目中**可行**。

核心依赖（pypdf、开放的 metadata 结构、已有的页码追踪机制）均已具备，改造不涉及架构变动，主要工作量集中在 `data_loader.py` 的 Outline 提取逻辑（约 60 行）。当前知识库以正式出版的技术手册为主，PDF 书签覆盖率高，改造后收益明显。

建议作为下一个迭代优先实现的功能点，无 Outline 文档的正则兜底可延后处理。
