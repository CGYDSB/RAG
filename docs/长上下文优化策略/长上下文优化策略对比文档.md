## 零、面试题解答

**问题：长上下文优化策略（Long-context Management）**

当用户进行多轮技术咨询，系统需携带前5轮对话历史+本次召回的5篇长文档（每篇5000+字），总Token可能超过20K。请设计一种上下文压缩或分层加载机制，在8K上下文窗口限制下保证回答质量，并说明哪些信息应保留、哪些可摘要或丢弃。

---

**当前项目的方案**

采用分层 Token 预算 + 对话历史增量压缩的策略：

```
总预算：7000 tokens（8K窗口留1K余量）
├── 系统提示：500 tokens（固定，永远保留）
├── 对话历史：1000 tokens（压缩后）
├── 检索文档：4000 tokens（按相关性截断）
├── 用户问题：200 tokens
└── 回答空间：1500 tokens（预留给 LLM 输出）
```

**信息保留优先级（从高到低）**：

1. 系统提示（角色定义 + 约束规则）——决定模型行为，永远保留
2. 最近 2 轮完整对话——保持对话连贯性
3. 早期历史摘要——LLM 增量压缩，保留核心问题和关键事实，丢弃重复信息和已解决细节
4. 当前轮检索文档——按相关性分数排序截断，低相关 chunk 丢弃
5. 用户当前问题——必须保留

**对话历史压缩策略**：超出 `keep_recent=2` 轮的历史用 LLM 增量压缩成摘要（不超过150字），只压缩上次摘要之后新增的旧轮次，避免重复压缩。

## 一、机制总览对比

| 维度 | 当前项目 | RAGFlow |
|------|----------|---------|
| 预算分配方式 | 静态分层预算（固定各部分上限） | 动态分配（知识块先占97%，历史用剩余） |
| 知识块截断 | 字符数估算（1 token ≈ 3字符），超800字符截断 | 精确 token 计数，按相似度排序后截断完整 chunk |
| 历史处理 | LLM 增量压缩成摘要（最近2轮完整保留） | 三级降级：全保留 → 丢弃中间历史 → 截断最大方 |
| 历史窗口 | 固定保留最近 N 轮（`keep_recent=2`） | Agent 模式：`window_size=13` 硬窗口；Dialog 模式：全传入后三级降级 |
| 历史内容截断 | 每条历史答案截断到 300 字符 | `form_history()` 每条截断到 2048 字符 |
| 生成预算控制 | 无（`max_tokens` 固定配置） | 动态：`min(用户设置, 模型窗口 - 实际输入token)` |
| 查询改写 | 已实现（`_rewrite_question`，含指代词时触发） | `full_question()`，多轮时自动触发 |
| 超限降级 | 无（超出预算时直接截断 chunk） | 三级降级，最终兜底截断最大方 |
| Token 计数 | 字符数估算（不精确） | `num_tokens_from_string()`（精确） |

## 二、逐模块详细对比

### 2.1 知识块（检索文档）的 Token 控制

**当前项目**（`_build_context_with_budget`）：

```python
budget_chars = self.token_budget['context'] * 3  # 4000 * 3 = 12000 字符
for i, chunk in enumerate(chunks):
    text = chunk.text
    if len(text) > 800:
        text = text[:800] + "..."   # 单个 chunk 截断到 800 字符
    if total + len(formatted) > budget_chars:
        break                        # 总量超限时停止
```

- 用字符数估算 token（1 token ≈ 3 字符），不精确
- 单个 chunk 超过 800 字符时截断，可能切断语义
- 超出预算时直接停止，不尝试塞入截断版本（实际上有 `remaining > 100` 的逻辑，但只对最后一个 chunk 生效）

**RAGFlow**（`kb_prompt`）：

```python
for i, c in enumerate(knowledges):
    used_token_count += num_tokens_from_string(c)  # 精确 token 计数
    chunks_num += 1
    if max_tokens * 0.97 < used_token_count:
        knowledges = knowledges[:i]   # 截断，不切割单个 chunk
        break
```

- 精确 token 计数
- 截断单位是完整 chunk，不会把一个 chunk 切一半（保证每个进入 Prompt 的 chunk 语义完整）
- chunks 已按相似度降序排列，截断的是相关性最低的 chunks

**差距**：当前项目对单个 chunk 做了 800 字符截断，可能破坏语义完整性。RAGFlow 不截断单个 chunk，而是整体丢弃低相关 chunk。

### 2.2 对话历史的处理

**当前项目**（`ConversationManager`）：

```
对话历史（N轮）
    ├── 最近 2 轮：完整保留（format_recent_history，答案截断到300字符）
    └── 更早的轮次：LLM 增量压缩成摘要（不超过150字）
```

- 主动压缩：超出 `keep_recent` 的历史用 LLM 压缩成摘要
- 增量压缩：只压缩新增的旧轮次，避免重复压缩
- 压缩失败时 fallback：截断拼接

**RAGFlow**（`message_fit_in` 三级降级）：

```
Level 1: 总量 < max_length → 全部保留
Level 2: 超限 → 丢弃中间历史，只保留 system + 最新 user
Level 3: 仍超限 → 截断最大方（系统 Prompt 或用户消息）
```

- 被动降级：不主动压缩，而是在超限时按优先级丢弃
- 不依赖 LLM 压缩（无额外 API 调用）
- 三级兜底，确保任何情况下都能生成答案

**差距**：

当前项目的 LLM 压缩方案在压缩质量上更好（摘要保留了语义），但每次压缩需要额外的 LLM 调用（增加延迟和费用）。RAGFlow 的三级降级不需要额外调用，但丢弃历史时可能损失上下文。

两种方案各有取舍，当前项目的方案对多轮对话质量更友好，RAGFlow 的方案对延迟和成本更友好。

### 2.3 生成 Token 预算控制

**当前项目**：

```yaml
# settings.yaml
llm:
  max_tokens: 1000  # 固定值
```

生成的 `max_tokens` 是固定配置，不考虑实际输入占用了多少 token。如果输入很长（接近 8K），固定的 1000 token 生成预算可能导致输出被截断。

**RAGFlow**：

```python
if "max_tokens" in gen_conf:
    gen_conf["max_tokens"] = min(gen_conf["max_tokens"], max_tokens - used_token_count)
```

动态计算：`生成预算 = min(用户设置, 模型窗口 - 实际输入token)`，确保输入 + 输出不超过模型上下文窗口。

**差距**：当前项目没有动态调整生成预算，在输入较长时可能导致输出被截断。

---

### 2.4 Token 计数精度

**当前项目**：

```python
budget_chars = self.token_budget['context'] * 3  # 1 token ≈ 3 字符（粗略估算）
```

字符数估算，中文字符和英文字符的 token 比例不同（中文通常 1 字符 ≈ 1-2 token，英文 1 token ≈ 4 字符），估算误差可能达到 2 倍。

**RAGFlow**：

```python
from rag.utils import num_tokens_from_string
used_token_count += num_tokens_from_string(c)  # 精确 token 计数
```

使用 tiktoken 精确计数，误差为 0。

## 三、当前策略可改进的地方

### 优先级 1：动态生成预算控制

当前 `max_tokens` 固定为 1000，不考虑实际输入长度。改为动态计算：

```python
# _generate_response() 中
input_chars = len(prompt)
estimated_input_tokens = input_chars // 3
max_window = self.max_total_tokens  # 7000
available_for_output = max(500, max_window - estimated_input_tokens)
config = GenerationConfig(
    temperature=...,
    max_tokens=min(self.config.get('llm', {}).get('max_tokens', 2000), available_for_output)
)
```

### 优先级 2：知识块不截断单个 chunk

当前对超过 800 字符的 chunk 做截断，可能破坏语义。改为整体丢弃低相关 chunk，而不是截断：

```python
# 改动前：超过 800 字符截断
if len(text) > 800:
    text = text[:800] + "..."

# 改动后：不截断单个 chunk，超出预算时整体跳过
if total + len(formatted) > budget_chars:
    break  # 直接跳过，不截断
```

### 优先级 3：精确 Token 计数

引入 tiktoken 替代字符数估算：

```python
# 需要安装：pip install tiktoken
import tiktoken
_encoder = tiktoken.get_encoding("cl100k_base")

def _count_tokens(text: str) -> int:
    return len(_encoder.encode(text))
```

对于中文文档，精确计数能避免因估算误差导致的预算超支或浪费。

### 优先级 4：历史超限时的三级降级兜底

当前如果 LLM 压缩失败，fallback 是截断拼接，可能导致 Prompt 超出窗口。加一个简单的三级降级兜底：

```python
# 在 query() 的 Prompt 格式化后，检查总长度
total_chars = len(prompt)
max_chars = self.max_total_tokens * 3
if total_chars > max_chars:
    # 超限：丢弃历史，只保留 context + question
    logger.warning(f"Prompt too long ({total_chars} chars), dropping history")
    prompt = template.format(context=context, question=question)
```

## 四、信息保留优先级总结

基于当前项目实现和 RAGFlow 对比，总结信息优先级：

| 信息类型 | 当前项目策略 | 建议策略 | 原因 |
|---------|------------|---------|------|
| 系统提示 | 始终保留 | 始终保留 | 决定模型行为的基础约束 |
| 高相关 chunk | 优先保留 | 优先保留，不截断单个 chunk | 直接决定回答质量 |
| 最新用户问题 | 始终保留 | 始终保留 | 当前任务的核心 |
| 最近 2 轮对话 | 完整保留（答案截300字） | 完整保留 | 多轮理解的直接上下文 |
| 早期对话历史 | LLM 压缩成摘要 | LLM 压缩成摘要 | 已融入摘要，原文可丢弃 |
| 低相关 chunk | 截断后保留 | 整体丢弃 | 截断后语义不完整，不如不放 |
| 生成空间 | 固定 1000 token | 动态计算 | 确保输入+输出不超窗口 |
