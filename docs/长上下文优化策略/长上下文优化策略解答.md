# 长上下文优化策略解答

**面试题**：长上下文优化策略（Long-context Management）

当用户进行多轮技术咨询，系统需携带前5轮对话历史+本次召回的5篇长文档（每篇5000+字），总Token可能超过20K。请设计一种**上下文压缩或分层加载**机制，在8K上下文窗口限制下保证回答质量，并说明哪些信息应保留、哪些可摘要或丢弃。

---

## 一、问题建模

典型的超长上下文场景：

```
系统提示（角色 + 9条规则）：~500 tokens
5轮对话历史：~3000 tokens
5篇文档召回（每篇5000字 → 切分后取 top-5 chunk）：~5000 tokens
用户当前问题：~200 tokens
─────────────────────────────────────────
合计：~8700 tokens  >  8K 窗口
```

核心矛盾：**对话历史和检索文档都很重要，但 token 预算有限**。

解法不是单一机制，而是一套**分层预算 + 主动压缩 + 多级兜底**的组合策略。

---

## 二、整体方案：分层 Token 预算

将 8K 窗口（留 1K 余量，实际用 7000 token）按优先级分层分配：

```
总预算：7000 tokens
├── 系统提示：500 tokens   ← 永远保留，决定模型行为
├── 对话历史：1000 tokens  ← 压缩后注入
├── 检索文档：4000 tokens  ← 按相关性截断
├── 用户问题：200 tokens   ← 永远保留，当前任务核心
└── 回答空间：1300 tokens  ← 动态计算，确保不超窗口
```

**信息保留优先级（从高到低）**：

| 优先级 | 信息类型 | 策略 | 原因 |
|--------|----------|------|------|
| 1 | 系统提示 | 始终保留 | 决定模型角色和约束规则 |
| 2 | 用户当前问题 | 始终保留 | 当前任务的核心 |
| 3 | 最近 2 轮完整对话 | 完整保留 | 保持对话连贯性，理解指代词 |
| 4 | 早期对话历史 | LLM 压缩成摘要 | 保留核心事实，丢弃细节 |
| 5 | 高相关检索文档 | 按相关性排序保留 | 直接决定回答质量 |
| 6 | 低相关检索文档 | 整体丢弃 | 相关性低，占用预算不值得 |

---

## 三、机制一：对话历史增量压缩

### 问题

5轮对话历史约 3000 token，超出分配的 1000 token 预算。

### 方案：最近 N 轮完整保留 + 更早轮次 LLM 增量压缩

```
对话历史（5轮）
    ├── 第4轮、第5轮：完整保留（~1000 tokens）
    └── 第1轮、第2轮、第3轮：LLM 压缩成摘要（~150 tokens）
```

**增量压缩**：只压缩上次摘要之后新增的旧轮次，避免重复压缩已处理的历史：

```python
class ConversationManager:
    def compress_history(self, generator, gen_config) -> str:
        older = self.get_older_turns()
        new_older = older[self._last_compressed_count:]  # 只处理新增的旧轮次

        if self.summary:
            # 在已有摘要基础上追加，而非全量重压缩
            compress_prompt = f"""
已有摘要：{self.summary}
新增对话：{new_history_text}
更新后的摘要（不超过150字）："""
        else:
            compress_prompt = f"""
将以下对话压缩为摘要（不超过150字）。
重点保留：核心问题、关键事实、未解决疑问。
丢弃：重复信息、寒暄、已解决细节。
对话历史：{new_history_text}
摘要："""

        result = generator.generate(compress_prompt, gen_config)
        self.summary = result.text.strip()
        self._last_compressed_count = len(older)  # 记录已压缩到第几轮
```

**压缩效果示例**：

```
原始历史（3轮，约1500 tokens）：
  第1轮 Q: 阿司匹林的禁忌症有哪些？
  第1轮 A: 阿司匹林禁用于对水杨酸类药物过敏的患者，活动性消化道溃疡患者禁用...（300字）
  第2轮 Q: 妊娠期可以用吗？
  第2轮 A: 妊娠晚期妇女应避免使用，可能导致胎儿动脉导管早闭...（200字）
  第3轮 Q: 那儿童呢？
  第3轮 A: 16岁以下儿童禁用，有瑞氏综合征风险...（150字）

压缩后摘要（约50 tokens）：
  用户询问阿司匹林禁忌症。已确认：过敏者、消化道溃疡、妊娠晚期、16岁以下儿童禁用。
```

**为什么选增量压缩而不是全量重压缩**：每次全量重压缩会把已经压缩过的摘要再压缩一遍，信息损失累积。增量压缩只处理新增的旧轮次，已有摘要直接复用，信息损失最小。

## 四、机制二：检索文档 Token 预算控制

### 问题

5篇文档召回，每篇 5000+ 字，即使只取 top-5 chunk，也可能超出 4000 token 预算。

### 方案：按相关性排序 + 精确计数 + 整体跳过

检索结果已按 `final_score` 降序排列，从最相关的 chunk 开始放入上下文，超出预算时整体跳过（不截断单个 chunk）：

```python
def _build_context_with_budget(self, chunks) -> str:
    budget_tokens = self.token_budget['context']  # 4000 tokens
    context_parts = []
    used_tokens = 0

    for i, chunk in enumerate(chunks):
        # 格式化：前置文件名和章节名
        filename = chunk.metadata.get('filename', '')
        section_path = chunk.metadata.get('section_path', '')
        header = ' | '.join(filter(None, [filename, section_path]))
        text = f"[{header}]\n{chunk.text}" if header else chunk.text
        formatted = f"[[{i+1}]] {text}"

        chunk_tokens = self._count_tokens(formatted)  # tiktoken 精确计数

        # 超出预算时整体跳过，不截断
        if used_tokens + chunk_tokens > budget_tokens:
            break

        context_parts.append(formatted)
        used_tokens += chunk_tokens

    return "\n\n".join(context_parts)
```

**为什么不截断单个 chunk**：截断可能发生在句子中间，LLM 看到残缺信息反而更容易产生幻觉（用自己的知识"补全"）。整体跳过低相关 chunk，保证每个进入 Prompt 的 chunk 都是完整的。

**精确 Token 计数**：引入 tiktoken，降级兼容字符估算：

```python
@staticmethod
def _count_tokens(text: str) -> int:
    try:
        import tiktoken
        enc = tiktoken.get_encoding("cl100k_base")
        return len(enc.encode(text))
    except ImportError:
        return len(text) // 2  # 中英混合降级估算（比 //3 更准确）
```

## 五、机制三：动态生成预算

### 问题

`max_tokens` 固定为配置值（如 1000），不考虑实际输入长度。当输入接近 7000 token 时，`输入 + 1000` 超过窗口，输出被截断。

### 方案：动态计算生成预算

$$\text{max\_output} = \max(300,\ W - T_{\text{input}})$$

$$\text{max\_tokens} = \min(\text{configured\_max},\ \text{max\_output})$$

```python
def _generate_response(self, prompt, chunks, question) -> RAGResponse:
    input_tokens = self._count_tokens(prompt)
    max_window = self.max_total_tokens          # 7000
    available_for_output = max(300, max_window - input_tokens)
    configured_max = self.config.get('llm', {}).get('max_tokens', 2000)

    config = GenerationConfig(
        max_tokens=min(configured_max, available_for_output)
    )
```

`max(300, ...)` 保证即使输入极长，也至少留 300 token 给输出，不会完全压缩到 0。

## 六、机制四：Prompt 超限兜底降级

### 问题

极端情况下（历史摘要本身很长 + 检索文档很多），即使经过前三层控制，最终 Prompt 仍可能超出窗口。

### 方案：超限时丢弃历史，只保留 context + question

```python
# query() — 格式化 Prompt 之后
prompt_tokens = self._count_tokens(prompt)
if prompt_tokens > self.max_total_tokens:
    logger.warning(f"Prompt too long ({prompt_tokens} tokens), dropping history")
    # 降级：丢弃对话历史，只保留检索文档 + 用户问题
    prompt = fallback_template.format(context=context, question=question)
```

这是最后一道防线，正常情况下不会触发。触发时打印 warning 日志，方便排查。

## 七、完整流程图

```
用户提问（第6轮）
         │
         ├─ 多轮消歧：含指代词时 LLM 改写为完整问题
         │
         ├─ 混合检索 → Top-5 chunks（按相关性排序）
         │
         ├─ 机制二：检索文档 Token 控制
         │     tiktoken 精确计数，按相关性顺序放入
         │     超出 4000 token 预算时整体跳过低相关 chunk
         │
         ├─ 机制一：对话历史压缩
         │     最近 2 轮完整保留
         │     第1-3轮 LLM 增量压缩成摘要（~150字）
         │
         ├─ Prompt 组装
         │     系统提示（500t）+ 历史摘要 + 最近2轮 + 检索文档 + 用户问题
         │
         ├─ 机制四：超限兜底检查
         │     prompt_tokens > 7000 → 丢弃历史重新组装
         │
         ├─ 机制三：动态生成预算
         │     max_tokens = min(配置值, 7000 - 实际输入token)
         │
         └─ LLM 生成答案
```

## 八、哪些信息应保留，哪些可摘要或丢弃

| 信息类型 | 处理策略 | 理由 |
|---------|----------|------|
| 系统提示（角色+规则） | 始终保留 | 决定模型行为，丢失后模型可能不遵守防幻觉规则 |
| 用户当前问题 | 始终保留 | 当前任务核心，不可丢失 |
| 最近 2 轮完整对话 | 完整保留 | 理解指代词（"它的剂量是多少"中的"它"）需要最近上下文 |
| 早期对话历史 | LLM 压缩成摘要 | 核心事实已提炼，原文冗余；摘要保留关键约束和已确认事实 |
| 高相关检索 chunk | 优先保留，不截断 | 直接决定回答质量；截断会破坏语义，引发幻觉 |
| 低相关检索 chunk | 整体丢弃 | 相关性低，占用预算不值得；放入反而可能误导 LLM |
| 生成空间 | 动态计算 | 固定值在输入长时会导致输出截断 |
