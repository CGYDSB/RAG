# 长上下文优化策略优化

参考来源：长上下文优化策略对比文档.md — 三、当前策略可改进的地方
改动文件：`src/rag_pipeline.py`

---

## 一、优化总览

| 优先级 | 问题 | 优化方案 | 改动位置 |
|--------|------|----------|----------|
| 1 | 动态生成预算缺失，输入过长时输出被截断 | 动态计算 `max_tokens = min(配置值, 窗口 - 输入token)` | `_generate_response()` |
| 2 | 单个 chunk 被截断到 800 字符，破坏语义完整性 | 超出预算时整体跳过 chunk，不截断 | `_build_context_with_budget()` |
| 3 | Token 计数用字符估算，中文误差可达 2 倍 | 引入 tiktoken 精确计数，降级兼容 | 新增 `_count_tokens()` |
| 4 | Prompt 超限时无兜底，可能导致 LLM 报错 | 超限时丢弃历史，只保留 context + question | `query()` |

## 二、优化一：动态生成预算控制

### 问题

`max_tokens` 固定为配置值（默认 2000），不考虑实际输入占用了多少 token。当输入较长（如多轮对话 + 大量检索文档）时，`输入 + 2000` 可能超过模型上下文窗口，导致输出被截断或 API 报错。

### 改动

```python
# src/rag_pipeline.py — _generate_response()

# 改动前
config = GenerationConfig(
    temperature=...,
    max_tokens=self.config.get('llm', {}).get('max_tokens', 2000)  # 固定值
)

# 改动后
input_tokens = self._count_tokens(prompt)
max_window = self.max_total_tokens          # 7000（8K窗口留1K余量）
available_for_output = max(300, max_window - input_tokens)  # 至少保留 300 token 给输出
configured_max = self.config.get('llm', {}).get('max_tokens', 2000)

config = GenerationConfig(
    temperature=...,
    max_tokens=min(configured_max, available_for_output)  # 取两者较小值
)
```

**逻辑**：`available_for_output = max(300, 窗口 - 实际输入token)`，确保输入 + 输出不超过模型上下文窗口。`max(300, ...)` 保证即使输入极长，也至少留 300 token 给输出，不会完全压缩到 0。

## 三、优化二：知识块不截断单个 chunk

### 问题

原实现对超过 800 字符的 chunk 做截断：

```python
# 改动前
if len(text) > 800:
    text = text[:800] + "..."
```

截断可能发生在句子中间，导致语义不完整。例如"函数调用时，实际参数会被引入被调函数的局部符号表，参数传递采用传值调用（传递的是对象的引用）"被截断为"函数调用时，实际参数会被引入被调函数的局部符号表，参数传递采用传值调用（传递的是对象的引..."，LLM 看到的是残缺信息。

### 改动

```python
# 改动后 — _build_context_with_budget()
chunk_tokens = self._count_tokens(formatted)

# 超出预算时整体跳过，不截断单个 chunk
if used_tokens + chunk_tokens > budget_tokens:
    break

context_parts.append(formatted)
used_tokens += chunk_tokens
```

超出预算时直接 `break`，整体跳过该 chunk 及后续所有 chunk（后续 chunk 相关性更低）。每个进入 Prompt 的 chunk 都是完整的，语义不会被破坏。

**权衡**：整体跳过意味着可能少放一个 chunk，但保证了已放入的 chunk 语义完整。对于 256 字符的 chunk_size，单个 chunk 约 100-200 token，预算利用率损失很小。

## 四、优化三：精确 Token 计数

### 问题

原实现用字符数估算 token：

```python
# 改动前
budget_chars = self.token_budget['context'] * 3  # 1 token ≈ 3 字符
```

中文字符通常 1-2 token/字符，英文约 0.25 token/字符，混合文本用固定比例估算误差可达 2 倍。估算偏低会导致实际超出窗口，估算偏高会浪费预算。

### 改动

新增 `_count_tokens()` 静态方法：

```python
@staticmethod
def _count_tokens(text: str) -> int:
    try:
        import tiktoken
        enc = tiktoken.get_encoding("cl100k_base")  # GPT-4/DeepSeek 使用的编码
        return len(enc.encode(text))
    except ImportError:
        return len(text) // 2  # 降级：中英混合 2.5 字符/token，比原来的 3 更准确
```

tiktoken 未安装时自动降级，不影响运行。降级估算从 `len // 3` 改为 `len // 2`，对中文文档更准确（原来的 3 字符/token 是英文标准，中文实际约 1.5-2 字符/token）。

安装 tiktoken（可选）：

```bash
pip install tiktoken
```

## 五、优化四：Prompt 超限时的兜底降级

### 问题

当对话历史很长、检索文档也很多时，即使经过预算控制，最终组装的 Prompt 仍可能超出窗口（例如历史摘要本身就很长）。原实现没有对这种情况做处理，可能导致 LLM API 报错。

### 改动

在 `query()` 格式化 Prompt 后，检查总 token 数，超限时丢弃历史重新格式化：

```python
# query() — 格式化 Prompt 之后
prompt_tokens = self._count_tokens(prompt)
if prompt_tokens > self.max_total_tokens:
    logger.warning(f"Prompt too long ({prompt_tokens} tokens), dropping history")
    try:
        fallback_template = self.prompt_manager.get('system.rag_assistant')
        prompt = fallback_template.format(context=context, question=question)
    except Exception:
        prompt = f"上下文：{context}\n\n问题：{question}\n\n回答："
```

**降级策略**：丢弃对话历史，只保留 context + question。这是最后一道防线，正常情况下不会触发（预算控制已经在上游处理了大部分情况）。触发时会打印 warning 日志，方便排查。
